# Stellar Wave: Reserve Attestation Expiry, Contract Storage Footprint, Alert Rule Dependency Graph, Maintenance Impact Preview

Four operational-monitoring features, each additive and independently deployable.

## 1. Reserve Attestation Expiry Monitor (#1041)

Tracks off-chain reserve attestations and flags ones approaching or past expiry.

- **Storage**: `reserve_attestations` (bridge, asset, attestor, `issued_at`/`expires_at`, lifecycle `status`).
- **Derived state**: expiry status (`valid` / `expiring_soon` / `expired` / `revoked`) is computed from `expires_at` at read time (`computeExpiryStatus` in `reserveAttestationExpiry.service.ts`) rather than stored, so it never drifts from the clock without a background job.
- **API**: `POST /api/v1/reserve-attestations`, `GET /api/v1/reserve-attestations`, `GET /api/v1/reserve-attestations/summary`, `GET /api/v1/reserve-attestations/:id`, `POST /api/v1/reserve-attestations/:id/revoke`.
- **Warning window**: defaults to 7 days, overridable per-request via `warningWindowDays`.
- **Rollback**: drop `reserve_attestations` (migration `20260827090000_reserve_attestations`); the routes 404 cleanly once the table is gone since queries only ever read/write this one table.
- **Support**: `GET /summary` is the fastest way to see what's about to lapse; `nextExpiring` is sorted soonest-first.

## 2. Contract Storage Footprint Dashboard (#1042)

Periodic snapshots of Soroban contract storage (entry counts, total bytes) so growth can be tracked before it becomes a rent/eviction problem.

- **Storage**: `contract_storage_snapshots`, one row per recorded snapshot per contract.
- **Ingestion**: `POST /api/v1/contract-storage/snapshots` — designed to be called by an external job/worker that reads ledger footprints; no RPC polling is bundled with this change.
- **Dashboard**: `GET /api/v1/contract-storage/dashboard` returns the latest snapshot per contract, ranked by size, each annotated with a `status` (`healthy`/`warning`/`critical`, thresholds overridable via `warningBytes`/`criticalBytes` query params) and a `trend`/`growthBytesPerDay` computed against the prior snapshot.
- **History**: `GET /api/v1/contract-storage/:contractId/history`.
- **Rollback**: drop `contract_storage_snapshots` (migration `20260827091500_contract_storage_snapshots`).

## 3. Alert Rule Dependency Visualizer (#1048)

Answers "what breaks if I change this alert rule?" by building a graph of alert rules and the suppression, escalation, and automation rules that reference them.

- **No new tables** — reads `alert_rules_v2`, `alert_suppression_rules`, `alert_escalation_rules`, and `automation_rules` directly.
- **Matching**: suppression/escalation/automation rules are linked to alert rules by asset-code overlap; an automation action whose `config.targetRuleId` (or `config.ruleId`) names a specific rule adds a stronger `controls` edge.
- **API**: `GET /api/v1/alert-rules/dependency-graph` (full graph), `GET /api/v1/alert-rules/dependency-graph/:ruleId` (subgraph around one rule).
- **Cycle detection**: `detectCycles` runs a DFS over the graph and reports any cycle (e.g. an automation rule that disables a rule which in turn re-enables the automation rule) in the `cycles` field — useful before wiring up automation actions that can loop.
- **Orphans**: `orphanRuleIds` lists alert rules nothing else depends on, i.e. safe to change without a ripple effect.
- **Rollback**: revert the route/service files; nothing is persisted.

## 4. Scheduled Maintenance Impact Preview (#1050)

Lets an operator see the blast radius of a proposed maintenance window **before** creating it.

- **No new tables** — reads `maintenance_windows`, `alert_rules_v2`, `external_dependencies`, and `alert_events`.
- **API**: `POST /api/v1/maintenance/impact-preview` with `{ scope, scopeIdentifier?, startTime, endTime }` (same shape as creating a window, but nothing is persisted).
- **Response**: overlapping existing windows in the same scope, the active alert rules and external dependencies that would be affected, an estimated alert volume for the window (historical 7-day alert rate for the affected assets, scaled to the window's duration), a `riskLevel` (`low`/`medium`/`high`), and human-readable `warnings`.
- **Risk model**: any overlapping window or affected critical-priority rule forces `high`; any other affected rule or an estimated volume above 5 forces `medium`; otherwise `low`.
- **Rollback**: revert the route/service files; nothing is persisted, so there is no data migration to undo.

## Testing

Each feature ships with unit tests under `backend/tests/services/` that mock the Knex connection and exercise both the pure computation helpers (expiry status, footprint status/growth, graph matching/cycle detection, scope matching/risk scoring) and the composed service methods. Run with:

```bash
npm run test:unit --workspace=backend
```
